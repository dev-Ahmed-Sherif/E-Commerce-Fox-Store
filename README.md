# Fox Store — فوكس ستور

A bilingual (Arabic / English) e-commerce storefront and admin dashboard for
**FoxWorksEG** — فوكس لأعمال الليزر والديكورات والأنتيكات — built with Next.js 14,
TypeScript, Tailwind CSS, Prisma and MongoDB.

The project started from a multi-store Next.js template and was rebranded and
extended for FoxWorksEG's laser-cut décor, wedding, graduation and gift
products. The storefront and dashboard were redesigned around a crimson,
charcoal and warm-amber palette with Arabic-first RTL support.

> Design notes and the redesign summary live in [`new design.md`](./new%20design.md).

---

## Overview

| Area | What it does |
|------|--------------|
| **Storefront** | Animated home page, category pages, product grids, cart, language and theme toggles |
| **Catalog dashboard** | Admin sign-in, overview stats, category and product CRUD, home/featured visibility toggles |
| **Customer accounts** | Sign up / sign in (email + password, optional Google), profile editing, current and last order panels |
| **Admin auth** | JWT access + refresh tokens in HttpOnly cookies, protected dashboard routes and APIs |
| **Checkout** | Cart → Stripe Checkout session → webhook marks the order paid |
| **Content** | Bilingual dictionaries, RTL/LTR layout switching, dark/light mode, local demo catalog |

The UI is designed to work **without a database** for demos: an in-memory
catalog (`src/lib/demo-data.ts`) powers the storefront and dashboard until
MongoDB/Prisma is wired in.

## Feature highlights

### Storefront

- Full-bleed hero with animated crimson/amber glows, grain overlay and a laser line.
- Home page sections for collections and featured products, with staggered
  Framer Motion reveals.
- Category landing pages with billboard imagery and responsive product grids.
- Sticky navbar with category links, cart badge, account menu, language and
  theme toggles, plus a search field that writes `?name=` to the URL. No page
  currently filters products by that query.
- Persistent client-side cart (`zustand` + `localStorage`).
- Footer with FoxWorksEG Facebook, WhatsApp and phone links.
- All product imagery is local under `public/catalog/`; the catalog copy is
  written in both Arabic and English.

### Dashboard (`/dashboard`)

- Animated admin login at `/dashboard/login`.
- Overview cards for total categories, products and featured products.
- Category management: create, edit, delete, image/billboard URL, Arabic name,
  and a “show on home” toggle.
- Product management: create, edit, delete, price, quantity, category, image URL,
  featured/archived toggles.
- Sidebar with brand logo, language toggle, theme toggle, store link and logout.
- Dashboard content is rendered in English or Arabic and is fully responsive.

### Accounts and orders

- Customer sign-up / sign-in pages at `/sign-up` and `/sign-in`.
- Profile page at `/profile` with personal details (name, phone, address, city,
  country) and two order summaries: the most recent unpaid order and the most
  recent paid order.
- The customer profile is stored in MongoDB via Prisma (`CustomerProfile`).

### Platform

- Arabic is the default locale; switching language updates
  `html[lang]` / `html[dir]` and persists to the `fox_locale` cookie.
- Dark/light mode uses `next-themes` and follows the system preference by default.
- Brand tokens (crimson, charcoal, amber, sand, wood) are defined as CSS
  variables for both themes and exposed to Tailwind.
- Fonts: **Outfit** for Latin, **Cairo** for Arabic, loaded with `next/font`.
- Image uploads are available through an admin-only UploadThing file router
  (4 MB per image, up to 4 images). The current dashboard forms accept image
  URLs rather than offering an upload control.

## Getting started

### Prerequisites

- Node.js 18.17+ (Node 20 LTS recommended)
- npm (the repo contains a `package-lock.json`)
- MongoDB local or Atlas — optional for the demo storefront, required for
  customer accounts, orders and the Prisma-backed admin APIs
- Optional: a Stripe account and Google OAuth credentials

### Install

```bash
npm install
```

`postinstall` runs `prisma generate`. If you change `prisma/schema.prisma`, run
it manually:

```bash
npx prisma generate
```

### Configure the environment

```bash
cp .env.example .env
```

On Windows PowerShell:

```powershell
Copy-Item .env.example .env
```

At minimum, set `DATABASE_URL`, `BETTER_AUTH_SECRET` and `BETTER_AUTH_URL`.
Add Stripe/Google/UploadThing values only if you use those integrations.

### Prepare the database

Generate the client, create the collections/indexes (including the `Role`
collection), then seed the role documents:

```bash
npx prisma generate
npx prisma db push
npm run db:seed
```

`prisma db push` is the MongoDB-appropriate command here because Prisma
Migrate does not support MongoDB migrations. Re-run `db:seed` whenever you add
a new role definition. When upgrading an existing database, also run:

```bash
npm run db:migrate-roles
```

### Run

```bash
npm run dev
```

Open <http://localhost:3000>.

### Demo admin login

The dashboard works without MongoDB using a hard-coded demo admin:

| Field | Value |
|-------|-------|
| Email | `admin@foxstore.eg` |
| Password | `foxadmin123` |

The login form is pre-filled with these values. Change or remove this account
before deploying to production.

`npm run db:seed` also creates database-backed admin users when the schema has
been pushed:

| Email | Role |
|-------|------|
| `super@fox-store.com` | `SUPER` |
| `admin@fox-store.com` | `ADMIN` |

The seed password defaults to `FoxStore@2026!`. Override it with
`SEED_DEFAULT_PASSWORD`, or use `SEED_SUPER_PASSWORD` / `SEED_ADMIN_PASSWORD`
for different passwords per account. Re-running the seed updates the role link
without resetting an existing password.

Google OAuth redirect URIs:

- Local: `http://localhost:3000/api/customer-auth/callback/google`
- Production: `https://YOUR_DOMAIN/api/customer-auth/callback/google`

MongoDB notes:

- Local standalone: `mongodb://localhost:27017/fox-store` — transactions are
  disabled automatically because standalone MongoDB cannot run multi-document
  transactions.
- Atlas or a replica set: transactions are enabled when the URI starts with
  `mongodb+srv://` or contains `replicaSet=`.

## Data model

`prisma/schema.prisma` defines the MongoDB collections used by the dashboard
and commerce APIs:

- `Role` — managed roles collection (`SUPER`, `ADMIN`, `SUBADMIN`, `CUSTOMER`,
  `USER`). Replaces the former Prisma `Role` enum.
- `User` — admin/dashboard user, bcrypt password, `roleId` relation to `Role`.
- `Store` — store owner and catalog root.
- `Billboard`, `Category` — category merchandising.
- `Size`, `Color` — product variants.
- `Product`, `Image` — catalog items and gallery images.
- `Order`, `OrderItem` — checkout records, payment state and line totals.
- `CustomerProfile` — storefront shopper details keyed by Better Auth user id.

### Roles as a collection

`Role` is a real MongoDB collection, not an enum. `User.roleId` points at a
`Role` document and the auth code reads the role name through
`include: { role: true }`. The schema and client are aligned, so run:

```bash
npx prisma generate
npx prisma db push
npm run db:seed
```

`db:seed` is idempotent and works on both standalone MongoDB and Atlas. On a
standalone server it writes the role documents through the MongoDB driver
because Prisma transactions require a replica set.

### Demo catalog

`src/lib/demo-data.ts` contains six categories and twelve bilingual products
(weddings, marriage contract, graduation, laser décor, models, practical gifts).
All demo prices are `0`, which the UI renders as “made to order.” Categories
and products added through the dashboard live in module memory only.

## Authentication and order flow

### Admin JWT flow

1. `POST /api/auth/login` validates the demo credentials or a Prisma user with
   bcrypt, loading the user together with its `Role` document.
2. `issueTokens()` signs a 15-minute access JWT and a 7-day refresh JWT with `jose`
   (HS256) and stores both in HttpOnly, `SameSite=Lax` cookies (secure in production).
3. The refresh token’s `jti` is recorded in an in-memory `Map`; refreshing revokes
   the old `jti` and issues a new pair.
4. `getSession()` verifies the access token and falls back to refresh rotation.
5. Dashboard API routes call `getSession()` / `isAdminRole()` before acting.

Caveats: the demo admin is hard-coded, the refresh-token store is process-local
(restarts and multi-instance deployments lose revocations), and middleware only
checks for cookie presence while the APIs perform the real verification.

### Customer flow

1. Better Auth is mounted at `/api/customer-auth` with the MongoDB adapter and
   `customer_*` collection names to avoid clashing with admin JWT routes.
2. Email/password is always enabled; Google is enabled only when both
   `GOOGLE_CLIENT_ID` and `GOOGLE_CLIENT_SECRET` are set.
3. The session is read server-side with `auth.api.getSession()` and client-side
   with `authClient.useSession()`.
4. The profile page creates a `CustomerProfile` row on first visit and links
   orders by the Better Auth user id (`customerUserId`).

### Checkout flow

1. The cart posts `{ productIds }` to `${NEXT_PUBLIC_API_URL}/checkout`.
2. `/api/[storeId]/checkout` loads the products from Prisma, counts duplicate ids
   as quantities, creates an unpaid `Order`, and opens a Stripe Checkout session
   in EGP with `orderId` in metadata.
3. Stripe redirects back to `/cart?success=1` (or `?canceled=1`).
4. `POST /api/webhook` verifies `Stripe-Signature`, then marks the order paid and
   copies the billing phone/address.

The checkout URL is inherited from the multi-store template: `NEXT_PUBLIC_API_URL`
must include the `/api/<storeId>` prefix for the cart to reach the route.

## Known limitations and production checklist

- **Demo catalog is not persistent.** Dashboard CRUD writes to an in-memory
  module; wire it to Prisma/MongoDB for real data.
- **Refresh-token revocation is in memory.** There is currently no durable
  refresh-token collection; add one (or a shared store) for multi-instance
  sessions.
- **Existing users need a `roleId`.** Documents created under the old enum
  schema still carry a `role` string. Run `npm run db:migrate-roles` after
  `db:seed` to backfill `roleId` from the matching `Role` document.
- **Demo admin credentials are hard-coded** in `src/app/api/auth/login/route.ts`
  and pre-filled in the login form. Remove or gate them in production.
- **`.env` is tracked by Git** (the `.gitignore` entry is commented out) and the
  working tree contains local secrets. Stop tracking it, rotate any exposed
  Stripe/Mongo/Google credentials, and commit only `.env.example`.
- **Checkout depends on `NEXT_PUBLIC_API_URL`** and the store-scoped route; set it
  to the full `/api/<storeId>` base for the cart to work.
- **Product detail pages are not implemented.** Product cards display
  information but do not link to a detail route, and the navbar search only
  updates the query string without filtering results.
- **No automated tests.** Only `tsc --noEmit` (which passes with the currently
  generated Prisma client) and ESLint are configured.
- `tmp-fb-photos/` is a scratch folder of Facebook photos and HTML used during
  content preparation; it is not referenced by the app.
- The npm package name is still `basewithnpm` from the original template.
